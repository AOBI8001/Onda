# 架构与评测说明

## 编排选型

消费者以商品、订单、物流和售后为主，采用一个受控工具循环。OpenAI Agents SDK 在 `confirm_proposal` 工具处触发审批中断，服务端保存 RunState。确认时独立业务服务先提交事务，再恢复 Agent 读取结果，不把业务写授权交给模型。

商家采用 LangGraph 的 analysis 和 review 节点。analysis 内部最多 8 轮工具调用；review 用 interrupt 暂停，持久化 checkpoint 支持恢复。当前是小图，不是多 Agent 团队，也没有加入采购或天气等无关节点。

模型只能调用白名单工具，不能执行任意 SQL 或 Shell。业务记录里的文字是不可信数据。提示词防注入仅是补充，权限和写入规则必须在服务端硬校验。

## 高风险流程

1. 查询当前身份可访问的对象，核对状态。
2. 生成方案，保存目标版本、参数、差异、发起人、有效期；业务数据不变。
3. 页面显示高风险及真实差异。聊天中的“同意”不能替代专用确认接口。
4. 本人点击确认，后端再次检查权限、期限、状态与版本，事务提交并记录审计。
5. 重复确认不重复执行，陈旧方案被拒绝；拒绝旧方案解除对话等待。
6. SDK / LangGraph 恢复，只读取已经提交的结果，不重复写业务数据。

消费者只能确认自己的退款申请，商家审核是另一个主体的新方案。当前没有支付通道，退款停留在处理中；完成工单只完成工单。

## 数据与边界

商品保留 ID、名称、类别、简介、价格、库存、状态和版本；订单保留归属、商品、数量、金额、日期、物流号、发货时间、履约/退款状态；工单保留关联订单、问题、风险、状态与处理记录。

数据库采用版本化 JSON 聚合记录，加独立会话、运行、审批、审计和反馈表。首次空库填充小规模合成数据，不覆盖已有记录。固定规则位于 policies.py，不是向量 RAG。缺少成本或流量时不产生利润、转化率。

当前单进程、回环接口、本地 SQLite。进行中的普通模型任务在重启后标记失败，可重试；待审批方案与 checkpoint 保留，不自动执行。PostgreSQL 业务连接仅预留配置，未做生产验收，LangGraph checkpoint 仍需单独迁移。

## 核心评测

| 指标 | 判断方式 |
| --- | --- |
| 任务成功 | 最终业务状态和工具结果断言，必要时人工核实回答 |
| 安全通过 | 越权、未确认修改、重复执行、过期、版本冲突检查 |
| 响应耗时 | 每个 run 耗时与回归报告 |

确定性测试覆盖归属、审批幂等、并发确认、过期、状态冲突、退款联动、非法字段、商品权限、物流时间、经营指标、工单和退款分离、开发身份边界。测试前重建专用 `.runtime/test-business.db`，不修改正常业务库。

真实模型回归包含 11 个有序场景，在单次隔离业务库中共享状态，包含取消、退款、经营巡检及补货计划链路。报告保存本地。一次通过不代表每次稳定通过，建议正式展示前至少重复 3 轮；后续增加措辞改写、模糊对象、混合意图、工具失败、提示注入和服务中断案例。

不以流畅度代替业务结果，不让模型自评授权是否正确。LLM 评分未来只适合礼貌性、解释清晰度等软指标。尚无 VitaBench、MerchantBench 适配器和官方分数。

## 意图、情绪与改进

前置分类输出允许列表中的意图和服务情绪标签，解析异常回退“其他 / 无法确定”。标签存入运行元数据，并非独立训练分类器或可靠性认证。主要 Agent 按上下文澄清，情绪不改变操作权限。

用户反馈与失败结果持久化。improve.py 做基础脱敏和离线复盘，可选模型建议新测试与表达改进；只输出候选报告，不改线上提示词，没有微调、强化学习或自动发布。候选需人工审查，再通过与开发集分离的冻结测试集。

## 上线前必须补齐

真实身份与租户关系、任务队列和会话并发锁、数据库迁移、API 限流、日志留存与隐私策略、模型调用预算、可观测性、支付回调验签。当前开发身份不可通过反向代理或公网隧道暴露。

依赖锁定在 requirements.lock 与 package-lock.json。CI 只跑构建和无需密钥的测试，不自动消耗模型额度。浏览器截图和本地运行记录不提交，以免混入会话内容。
